RDP Issue Monitor v1.2.2 安装说明

本版本新增：将 upstream 已收集的所有唯一 INI Candidate，逐一与 Repository 当前正式 rdpwrap.ini 比较。

一、需要替换的文件（3 个）
1. .github/workflows/rdp-monitor.yml
2. .github/scripts/rdp_issue_monitor.py
3. tests/test_rdp_issue_monitor.py

将 ZIP 内相同路径的文件完整替换到 johnson4860/rdp。不要只复制部分代码。

二、必须保留的文件
- rdpwrap.ini：正式 Production INI，绝对不要用本包中的文件覆盖它。本版本会读取当前 checkout 中的这份文件作为比较基准。
- monitor-state.json：保留现有监控检查点。
- compatibility-candidates.json：保留已收集的 Candidate 数据库。

三、安装步骤
1. 打开 GitHub Repository：johnson4860/rdp。
2. 依次打开以上三个文件，点击 Edit。
3. 用 ZIP 中对应文件的完整内容替换。
4. 每个文件 Commit changes（可分开提交）。
5. 确认三个文件都已更新到 main。
6. 打开 Actions > RDP Update Monitor > Run workflow。

四、自动生成的新文件
production-comparison.json
此文件不需要手动创建。Workflow 成功执行后会自动生成并提交。

五、在哪里看比较结果
打开 Actions 中最新一次 RDP Update Monitor Run，查看 Summary 的：
Upstream INI vs Production INI comparison

结果分类：
- exact_match：Candidate 的所有 Section 和 Key/Value 与 Production 对应内容完全相同。
- partial_match：Candidate 的内容都能在 Production 找到，但 Production 还有额外 Key。
- new_section：Candidate Section 在 Production 中不存在。
- new_keys：同一 Section 内，Candidate 有 Production 没有的 Key。
- value_difference：同一个 Section/Key 的值不同，会显示 Candidate 值和 Production 值。
- mixed_difference：同一 Candidate 同时存在多类差异。
- incomplete：Candidate 结构不完整；系统仍会比较其中可识别的完整 Section，并标记未分组的 Key/Value。

六、比较规则
- Section 名称和 Key 名称忽略大小写。
- Value 去除两端空白后进行精确比较，不忽略值大小写。
- 如果 Production 多出 Key，会标记 partial_match，不会误报 exact_match。
- 如果 Candidate 缺主 Section Header，缺失 Header 前的 Key/Value 不会被擅自补入，也不会拿去错误比较。
- JSON 会记录 Production rdpwrap.ini 的 SHA-256、[Main] Updated 值、Section 数量和运行时的 GITHUB_SHA。

七、重要安全边界
- Monitor 只读取公开 GitHub Issue/Comment 和 Repository 内 rdpwrap.ini。
- 不下载、运行或安装 termsrv.zip。
- 不修改、不覆盖、不发布正式 rdpwrap.ini。
- exact_match 只代表配置文本与 Production 相同，不代表已在 Windows 上测试成功。
- 所有 Candidate 仍须人工审核及隔离环境验证。

八、故障排查
如果 Summary 显示找不到 rdpwrap.ini：
- 检查 Repository 根目录是否存在 rdpwrap.ini。
- 确认 Run workflow 选择 main branch。
- 不要把 rdpwrap.ini 移到子目录。

如果 API 返回 403：
- 确认 Workflow monitor step 保留 GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}。
- 确认 permissions 中保留 issues: read 和 contents: write。

九、测试
Workflow 会先运行 tests/test_rdp_issue_monitor.py，再运行监控和比较。测试失败时不会继续执行上游扫描。
